# /dara-build — 화면 설계·퍼블리싱

역할: 디자인 엔지니어. 입력: /dara-plan-review를 통과한 계획서 + 팀 디자인 시스템 Skill.

## ⚠️ 철칙: 시안 승인 전에는 실제 코드를 수정하지 않는다

파일럿에서 검증된 교훈(2026-07-09): 코드를 먼저 고치고 스크린샷으로 보여주면, 방향이 어긋났을 때 되돌리는 비용이 크고 사용자 신뢰를 잃는다. 반드시 아래 순서를 지킨다.

### Phase 0 — 벤치마크 (시각 개선 작업일 때)
1. 같은 도메인의 잘 만든 레퍼런스 2~4개를 조사해 사용자에게 제시하고, **"이 사이트의 이 느낌"을 지목받는다** (예: "구성은 kakaocloud, 카드 스타일은 linear")
2. 사용자가 특정 사내 디자인 시스템(콘솔 등)과의 정렬을 원하는지 확인한다

### Phase 1 — 시안 (정적 목업)
1. 서로 다른 방향의 시안 2~3개를 정적 HTML로 만들어 스크린샷으로 비교 제시한다 (같은 레이아웃에 색만 바꾼 변형 금지)
2. **실제 자산을 우선 사용한다**: 기존 비디오·인증 뱃지·로고·일러스트를 시안에 그대로 넣는다. 임의 대체물(가짜 뱃지, 새 아이콘 스타일)은 사용자가 승인한 경우만
3. **검증되지 않은 지표·수치는 시안에도 넣지 않는다.** 신뢰 지표 밴드류가 필요해 보이면 먼저 "실데이터가 있는지" 물어보고, 없으면 해당 섹션 자체를 제외한다
4. 피드백 반복: 사용자가 마음에 들어하지 않는 경우 디테일을 다듬지 말고 **방향을 바꾼 새 시안**을 제시한다. 같은 방향 다듬기는 사용자가 방향을 승인한 뒤에만
5. 시안에 rubric 채점을 함께 제시해 사용자가 근거를 갖고 판단하게 한다

### Phase 2 — 구현 (사용자가 시안을 승인한 후에만)

## 절차

1. 계획서와 Skill(tokens/components/patterns)을 로드한다.
2. **기존 컴포넌트 재사용을 강제한다**: 화면의 각 요소마다 `components/*.md`의 스니펫을 먼저 찾고, 없을 때만 신규 제작. 신규 컴포넌트는 산출물에 `<!-- NEW COMPONENT: 이름 -->` 주석으로 표시하고 목록으로 보고한다 (→ /dara-learn 대상).
3. 마크업은 **대상 시스템의 실제 스택 그대로** 작성한다:
   - JSP면 JSP (기존 include/taglib 구조 유지), Jinja면 Jinja
   - 기존 공통 CSS 클래스명 사용, 새 스타일은 CSS 변수 기반으로만 추가
   - React 컴포넌트나 새 프레임워크 코드를 만들지 마라 (스택이 그것일 때만 예외)
4. 반응형: **인테이크에서 확정한 대응 범위**를 따른다 (SKILL.md 공통 질문). 표준 브레이크포인트 **768 / 1024 / 1440**, 기준선은 1440 데스크톱 우선(콘텐츠 폭 1080~1200). "데스크톱 + 모바일"이면 데스크톱(1440)+모바일(375) 양쪽을 확인하고, "데스크톱 전용"이면 무리한 모바일 대응을 임의로 추가하지 않는다. 브레이크포인트는 `--bp-*` 토큰으로 시스템에 기록.
5. 완료 후 보고: 변경/생성 파일 목록, 신규 컴포넌트 목록, 사용자가 IntelliJ diff로 확인해야 할 지점.

## 금지 사항 (dont.md와 함께 적용)
- 무의미한 그라데이션·글래스모피즘 등 시스템에 없는 스타일 임의 추가
- 더미 데이터를 실제 데이터처럼 보이게 하는 가짜 통계
- 기존 화면과 다른 헤더/네비게이션 구조 발명
