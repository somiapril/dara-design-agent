# /dara-review — 제작 후 디자인 감사

역할: 디자인 QA. 시점: 화면 구현 **후** (배포 전 또는 배포 후).

## 절차

1. /dara-plan-review가 만든 최종 계획서를 로드한다 (없으면 Skill만으로 진행).
2. **실제 렌더링을 확인한다**: 브라우저에서 화면을 열어 스크린샷을 찍는다 (Playwright, 브라우저 도구, 또는 사용자가 스크린샷 제공). 코드만 읽고 평가하지 마라 — 렌더링 결과가 기준이다.

   **점검 절차 (Live Environment First — 코드보다 렌더링을 먼저 본다):**

   1. **상호작용**: 주요 사용자 흐름을 직접 실행. 버튼 hover/active/disabled, 파괴적 액션의 확인 절차
   2. **반응형·테마**: 반응형은 인테이크 확정 범위 기준 — "데스크톱 + 모바일"이면 데스크톱(1440) + 모바일(375) 양쪽, 필요 시 태블릿(768) 추가. "데스크톱 전용"이면 1440만 확인하고 기록. 다크모드 지원 화면은 라이트/다크 양쪽 스크린샷으로 확인
   3. **시각 완성도**: 정렬·간격·타이포·색상 일관성 (rubric 2~4번 차원과 연결). 카드/컨테이너 안에 주입되는 콘텐츠(테이블·플러그인 위젯)의 내부 패딩 확인 포함
   4. **접근성**: 키보드 내비게이션, 포커스 상태, 레이블, 대비 4.5:1 (rubric 6번)
   5. **견고성**: 폼 검증 에러, 긴 텍스트 오버플로우, 로딩/빈/에러 상태 (rubric 5번)
   6. **코드 품질**: tokens.md 값 사용 여부, components/ 재사용 여부 (rubric 3번)
   7. **콘텐츠·콘솔**: 오탈자, placeholder 잔존, 콘솔 에러

3. `rubric/review-checklist.md`의 **동일한 7개 차원을 같은 방식으로 재채점**하고, 계획 단계 점수와 비교한다.
4. 발견된 문제를 **4단계로 분류**하고 수정한다:
   - **[Blocker]** 배포 불가 결함 → 즉시 수정
   - **[High]** 이번 작업 내 수정
   - **[Medium]** 후속 작업으로 기록
   - **[Nitpick]** 사용자 판단에 위임
   - 수정 1건 = 커밋 1건 (원자적 커밋, 메시지에 어떤 차원의 문제인지 명시)
   - 각 수정마다 **before/after 스크린샷** 첨부
5. 최종 보고: 차원별 점수 변화표, 분류별 문제·수정 목록, 남은 이슈(수정하지 않기로 한 것과 이유).

## 보고 원칙
- 잘된 점 1~2개를 먼저 언급한다.
- 처방("margin을 16px로")이 아니라 문제와 영향("항목 간 간격이 불규칙해 그룹핑이 안 보임")을 서술한다.
- 시각 문제에는 반드시 스크린샷을 붙인다.

## 규칙
- 계획서와 구현이 다르면 "구현을 계획에 맞추는 것"이 기본. 구현이 더 나은 경우에는 사용자 확인 후 계획서를 갱신.
- 이 과정에서 검증된 새 패턴이 있으면 /dara-learn 실행을 제안하라.
- 사용자가 IntelliJ diff로 확인하기 전에는 push하지 않는다.
