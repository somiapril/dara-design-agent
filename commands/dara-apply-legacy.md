# /dara-apply-legacy — Case B 레거시 적용 가이드 (보완)

역할: 디자인 시스템 아키텍트. 대상: `/dara-extract`로 추출·정규화한 뒤 **운영 중 레거시 화면에 실제로 적용**하는 단계.
extract는 "추출·정규화·자산화"까지 다룬다. 이 문서는 그 다음 — **적용 단계에서 반복적으로 부딪히는 함정과 검증 기법**을 정리한다. (예시 스택: Flask+Jinja+jQuery + 상용 JS 그리드 컴포넌트)

## 0. 원칙 — 무수정 오버레이 우선

- 기존 CSS 파일은 **건드리지 않는다.** `tokens.css`(:root 변수) + `theme.css`(오버라이드) 두 파일을 만들어 **모든 기존 CSS 다음(가장 마지막)** 에 로드한다. base/common 템플릿에 `<link>` 2~3줄만 추가 — 이게 유일한 마크업 변경이고, 롤백은 링크 제거로 끝난다.
- 색은 하드코딩 금지, 시맨틱 토큰만. 값 변경엔 근거를 남긴다.
- 버튼 의미 구분처럼 CSS만으로 불가능한 것만 **최소한의 마크업 클래스 추가**로 처리한다.

## 1. Specificity(우선순위) 함정 — 반드시 점검

레거시 CSS는 `.a.b.c` 다중 클래스와 `!important`가 흔하다. 오버라이드가 "안 먹으면" 십중팔구 원본이 더 높은 우선순위다.

- 오버라이드 전, 원본 선언을 grep해서 **셀렉터 specificity를 확인**하고 동일하거나 더 높게 맞춘다.
- 실제 사례: 상용 JS 그리드 헤더의 진한 top-border가 `.headercell.cell-header-lastrow.cell-header-firstrow`(0,4,0)에 정의돼 있어, `.grid .headercell`(0,2,0) 오버라이드를 이기고 그대로 남았다 → 같은 다중클래스 셀렉터까지 함께 지정해야 이긴다.
- 원본이 `!important`면 오버라이드도 `!important`.

## 2. 색의 맥락 분리 — 한 색이 두 역할

레거시는 같은 색(예: 브랜드 레드 `#ea0530`)이 **primary 액션과 danger를 겸용**하는 경우가 많다.

- 셀렉터별로 맥락을 나눠 매핑: 액션·브랜드·선택상태 → `--color-primary`, 에러·필수·삭제 → `--color-danger`.
- **CSS-only의 한계**: 같은 클래스(`.bg-red`)가 조회 CTA와 삭제를 동시에 쓰면 오버레이만으론 못 나눈다. 이때는 한계를 사용자에게 명확히 알리고, 해당 버튼 마크업에 구분 클래스(`.btn-danger-outline` 등)를 **선별 추가**한다. 버튼은 대개 id로 JS 바인딩되므로(먼저 grep 확인) class 교체는 안전하다.
- 파괴적 액션(삭제·폐기)은 반드시 danger로 분리하고, 한 버튼 그룹에 solid primary는 하나만.

## 3. PNG 스프라이트 아이콘 → SVG (마크업 무수정)

아이콘 버튼이 PNG 스프라이트(`background: url(...png)`)면 CSS만으로 현대화할 수 있다.

- 아이콘은 `::before`에 SVG data-URI로 그린다. **요소 자체에 `mask`를 걸면 border까지 잘리므로** 반드시 `::before` 사용.
- 색은 SVG에 baked(기본 뉴트럴, 삭제 danger) 하거나 `currentColor` + `mask`.
- hover 시 원본의 `background:#eee url(hover.png)` shorthand가 스프라이트를 되살리지 않도록 hover 상태에도 `background-image:none` 유지.
- 자주 쓰는 변형만 우선 커버하고, 화면 진단에서 새로 발견되는 변형(예: `btn-arrow_up`, `btn-user_add`)은 그때그때 세트에 추가한다.

## 4. JS 렌더 그리드(상용 그리드 컴포넌트 등) — CSS만으로 안 되는 것

목록이 JS로 그려지면 상태 뱃지·데이터는 CSS 밖이다.

- 상태 컬럼을 뱃지로 바꾸려면 그리드 **셀 render 함수**를 뱃지 헬퍼로 교체한다.
- 백엔드가 없는 퍼블리싱 저장소는 그리드가 빈다("데이터가 없습니다"). `getGridData`의 success(빈 결과)와 **error 양쪽**에 샘플 데이터 폴백을 주입해 화면을 채운다. 이런 보조 코드는 별도 파일(`*-ui-extras.js`)로 분리해 운영 배포 시 제거 가능하게 한다.

## 5. 검증 — 에이전트는 실제 앱에 접근 못 함

로컬 서버(localhost)에 접근할 수 없다. 그래도 렌더 검증은 한다.

- **실제 CSS 체인을 스테이징**(기존 앱 CSS + tokens.css + theme.css)하고, 대표 마크업(실제 클래스명)으로 목업 HTML을 만들어 headless 브라우저(프리인스톨 chromium/playwright)로 스크린샷 → 오버라이드가 실제 선택자 위에서 먹는지 눈으로 확인한다.
- 자립형 **컴포넌트 레퍼런스(스타일가이드 HTML)** 를 저장소에 두고(뷰 가능한 라우트) 이후 모든 적용의 시각 기준으로 삼는다.
- 마지막에 "실제 화면 확인은 사용자 몫(하드 새로고침 권장)"임을 안내한다.

## 6. 진행 순서 — "뭐가 바뀐지 모르겠다" 방지

여러 diff가 흩어지면 사용자가 변화를 파악 못 한다. 순서를 지킨다.

1. **컴포넌트 레퍼런스(코드 내 HTML)를 먼저** 만든다 — 버튼·아이콘버튼·데이터테이블 등 + 각 컴포넌트에 사용 class 주석. 사용자가 기준점을 갖는다.
2. 대상 화면을 **진단**(현재 마크업의 버튼·아이콘·테이블·필터·상태를 나열).
3. **변경 계획**을 표로 제시(현재 → 변경, 이유).
4. **적용** — 우선순위 순(색·위계 → 아이콘 → 폼 디테일 → 구조).

## 7. 그 밖의 레거시 하드값

- 타이포가 rem/px 혼용에 큰 편이면 밀도 프리셋으로 축소(예: 타이틀 1.7rem→18px, LNB 1.13rem→13.5px).
- `min-width:1880px` 같은 하드 하한도 조정 대상(반응형 아니어도 하한만 축소 가능).
- 인테이크 답변이 서로 모순되면(예: "블루로 통일" + "primary=레드 유지") 하나로 재확인 후 진행.

## 8. 오버레이 회귀 체크리스트 (실전에서 자주 놓침)

오버라이드는 원본을 "부분만" 덮으면 회귀가 난다. 적용 후 반드시 점검한다.

- **속성 전량 덮기**: 원본 색/상태 규칙은 보통 `color`+`background`를 함께 지정한다. 오버라이드도 **둘 다** 지정하라. (예: LNB `li>a:hover`가 `color:#ea0530; background:#fff` → 배경만 바꾸면 **글자 레드가 남는다.**)
- **hover/selected의 실제 DOM 클래스 확인**: JS가 만드는 마크업을 봐야 셀렉터가 맞는다. (예: `common.js`가 상위 `<a>`에 `.selected`를 토글하고 `<li>`엔 `.expanded`를 준다 → CSS 파일만 보고 `li.selected`로 짐작하면 빗나감.) 안 먹으면 JS의 DOM 생성 코드를 grep한다.
- **스프라이트를 CSS로 숨기면 "전량 대체"**: `.btn-ico{background-image:none}`로 스프라이트를 죽이면 SVG를 안 준 변형은 **빈 박스**가 된다. 화면에 쓰이는 변형을 **전부 grep**해서 열거하고(`grep -rhoE "btn-ico[^'\"]*"`), 못 채운 것 대비해 base에 **폴백 아이콘(--ico)** 을 둔다.
- **hover 텍스트 대비 명시**: 모든 버튼 variant의 `:hover`에 `color`를 명시한다(솔리드=흰색, outline=자기 색). 안 하면 원본 hover 규칙 탓에 텍스트가 저대비/사라진다. **외부 프레임워크(상용 그리드·UI 프레임워크, Bootstrap 등, 목업엔 없고 실제 앱에만 로드)가 `.btn:hover{color:#fff}`로 덮는 경우가 있다 — 이땐 오버라이드에 `!important`를 붙여 이긴다. 단 `!important`를 한 variant에 쓰면 다른 variant hover도 `!important`로 맞춰 충돌을 막는다(예: outline을 !important로 하면 solid의 흰색도 !important).**
- **레거시 기본 크기 점검**: `.Button.btn` 기본이 48px처럼 크면 액션바 등은 표준(≈36px)으로 축소. `.btn_sx` 같은 초소형 유틸이 붙어 있으면 제거.
- **긴 상세화면 구조**: 섹션이 많아 스크롤이 길면, **JS로 그려지는 그리드·에디터(CodeMirror 등)가 있는 화면은 hide/show 탭을 쓰지 마라** — 초기 로드 시 숨겨진 컨테이너는 폭 0으로 계산돼 그리드가 깨진다. 대신 **sticky 섹션 네비(칩형 목차 + IntersectionObserver 스크롤스파이) + sticky 하단 액션바**로 탐색성을 준다(모든 섹션은 렌더 유지). 진짜 탭이 꼭 필요하면 탭 전환 시 그리드 resize/refresh 훅을 붙이고 라이브 테스트한다.

## 9. 검증 루프 — 사용자 스크린샷이 최선

에이전트는 라이브 앱(localhost)을 못 본다. **가장 효율적인 검증은 사용자 스크린샷**이다 — 목업 렌더로 1차 확인하고, 체크포인트마다 사용자에게 실제 화면 스크린샷을 요청해 회귀를 잡는다. "코드로 진행 vs 화면 접근"은 양자택일이 아니다: 작업은 코드에서 하고(그게 유일한 적용 경로), 확인만 스크린샷으로 닫는다. (로컬 서버 접근은 실행 위치를 바꿔도 안 되므로 스크린샷 루프가 정답.)
