# /dara-extract — 기존 코드베이스에서 디자인 시스템 추출

역할: 디자인 시스템 아키텍트. 대상: 디자인 시스템이 없는 운영 중 시스템 (Case B의 1단계).

**산출물 위치 규칙: 모든 산출물은 대상 서비스 저장소 안에 생성한다.** 인벤토리 리포트(`extract-report.md`), 디자인 시스템 Skill, tokens.css, 프리뷰가 전부 해당된다 — 리포트는 Skill의 "왜 이렇게 정했나" 근거 문서이므로 Skill과 함께 그 서비스 저장소에서 버전 관리되어야 하고, 서비스를 이어받을 다른 개발자도 볼 수 있어야 한다. 개인 폴더나 에이전트 폴더에 남기지 않는다.

## 절차

### 1. 인벤토리 스캔
- 스타일 정의 전체에서 수집 (CSS/SCSS, CSS-in-JS, 테마/스타일 상수 파일): 색상값(hex/rgb — **사용 빈도순 정렬**), font-family/size/weight, 간격 값(margin/padding 빈도), border-radius, box-shadow
- 마크업을 생성하는 코드에서 수집 (JSP/Thymeleaf/Jinja/PHP 등 서버 템플릿, React/Vue 컴포넌트, HTML 문자열을 조립하는 서버 코드 포함): 버튼, 테이블, 폼 입력, 카드, 모달, 알림/메시지의 **마크업 변형 전부** (클래스명 + 실제 스니펫)
- 인라인 스타일과 페이지 전용 CSS도 포함 (레거시에서는 여기에 실체가 있음)
- 스택이 HTML 기반이 아니어도(예: 스타일이 JS 객체나 서버 코드에 흩어져 있어도) 위 두 종류가 존재하면 추출 가능. 웹이 아닌 네이티브 UI는 인벤토리까지만 지원(스크린샷 리뷰 루프는 브라우저 전제)
- **`component-checklist.md`를 점검표로 사용**: Tier 1~3 컴포넌트 각각이 코드에 "있음 / 변형 난립 / 없음" 중 무엇인지 표시한다. 없거나 난립하면 각각 신규 제작·정규화 대상이 된다 (디자인 시스템이 없는 팀일수록 이 점검이 로드맵이 됨).

### 2. 비일관성 리포트 산출
다음 형식으로 보고:

```
## 색상: 총 23개 발견
- #1a73e8 (127회) — 주요 액션 ← primary 후보
- #1b74e9 (3회) — #1a73e8의 오타로 추정 → 통합 권장
...
## 버튼: 7가지 변형 발견
- .btn-primary (형태 1) — 34개 화면
- 인라인 스타일 버튼 (형태 5) — 2개 화면 → .btn-primary로 통합 권장
```

### 3. 정규화 제안 (사용자 승인 필요)
- 변형들을 대표 패턴으로 수렴시키는 매핑표 제시 (예: 버튼 7종 → 2종)
- **기존 CSS 위에** CSS 변수 레이어 추가안 제시: `:root { --color-primary: #1a73e8; ... }`
- 기존 클래스명은 절대 삭제하지 않음. 값만 변수 참조로 교체하는 diff 제안

### 4. Skill 생성
승인된 결과를 `templates/design-system-skill/` 포맷으로 저장:
- `tokens.md` — 실제 CSS 변수·클래스명 기준
- `components/*.md` — **실제 코드베이스에서 복사한 마크업 스니펫** 포함 (새로 지어내지 말 것)
- `patterns.md` — 목록/상세/폼 등 화면 유형별 실제 레이아웃 구조

### 5. 컴포넌트 프리뷰 생성 (사용자가 눈으로 검증하는 단계)
원칙: **프리뷰는 실물을 참조한다.** 스타일·컴포넌트를 프리뷰에 복사하지 않는다 (drift 방지). 스택을 감지해 다음 중 하나로 생성:

- **SSR (JSP/Jinja/PHP 등)** → `preview.html` 한 장: 서비스의 **실제 공통 CSS를 `<link>`로 참조**하고, components/의 스니펫을 변형·상태(hover/disabled)별로 나열 (`templates/design-system-skill/preview.html` 골격 사용)
- **React/Vue** → 앱 내부에 `/_design/preview` 라우트 생성: **실제 컴포넌트를 import**해 변형·상태별로 렌더링. 개발 환경에서만 노출(운영 빌드 제외). 토큰은 theme 파일/tailwind.config에서 추출해 스와치로 표시
- **Storybook을 이미 사용 중** → 새로 만들지 말고 기존 스토리를 프리뷰 소스로 지정

생성 후 사용자에게 프리뷰를 열어 "추출된 컴포넌트가 실제 서비스 모습과 같은지" 확인받는다. 다르면 추출을 수정한다 (프리뷰를 고치는 게 아니라).

## 금지 사항
- 코드에 없는 색상/컴포넌트를 "더 나아 보인다"는 이유로 추가하지 마라 (개선은 /dara-plan-review 단계의 일)
- 프레임워크 교체 제안 금지 (JSP → React 등)
